# スクレイピングの対象範囲と巡回設計

物件データをどの都道府県から、どれだけの頻度で取りに行くかの設計。
`src/lib/scrapeTargets.ts` が唯一の情報源で、このドキュメントはその背景を残す。

---

## 1. なぜ「県を足すだけ」では済まないのか

### 負荷は県数では増えない

`nifty_extractor.ts` はページを 1 枚取るごとに 2〜4 秒（平均 3 秒）待つ。
したがって相手サーバーへのリクエスト頻度は

```
リクエスト頻度 ≒ max-parallel ÷ 3 秒
```

で、**対象県の数は式に出てこない**。県を 12 から 47 に増やしても、
並列数が 3 のままなら負荷は毎秒 1 リクエストのまま変わらない。

### 増えるのは実時間

代わりに 1 回の実行にかかる実時間が伸びる。

```
実時間 ≒ max(最長ジョブ, 全ジョブの分数の合計 ÷ max-parallel)
```

12 県 × 100 分 ÷ 並列 3 = 400 分（6.7 時間）だったものが、
47 県ではそのままだと 1600 分（26.7 時間）になる。
**日次 cron の 24 時間を超える。** `concurrency` は
`cancel-in-progress: false` なので、追い越した実行は待たされ、
実質その日の巡回が飛ぶ。

### つまり選択肢は 2 つしかない

| したいこと | 手段 | 代償 |
|---|---|---|
| 県を増やして鮮度も保つ | `max-parallel` を上げる | 相手サーバーへの負荷が比例して増える |
| 県を増やして負荷は据え置く | 巡回間隔を延ばす | 鮮度が落ちる |

県数は関係ない。**負荷と鮮度の直接のトレードオフ**である。

---

## 2. 採った方針

首都圏 4 県（東京・神奈川・埼玉・千葉）を追加して 16 県にする。
同時に、全県を毎日回すのをやめて階層を作る。

| 階層 | 対象 | 頻度 |
|---|---|---|
| `metro` | 在庫が多く検索需要も高い 10 県 | 毎日 |
| `regional` | 在庫が少ない 6 県 | 3 日に 1 回（位相をずらす） |

並列数は 3 → 4。負荷は約 +33%（毎秒 1 → 1.3 リクエスト）に留める。

### 結果

| | 12県 | 16県 | 47県（現在） |
|---|---|---|---|
| 並列数 | 3 | 4 | 4 |
| リクエスト頻度 | 約 1/秒 | 約 1.3/秒 | 約 1.3/秒 |
| 1 日あたりの合計分数 | 1200 分 | 1355 分 | 約 2050 分 |
| 1 日あたりのジョブ数 | 12 | 12 | 23〜24 |
| 最長ジョブ | 100 分 | 300 分（東京） | 300 分（東京） |
| **実時間の見積もり** | **6.7 時間** | **5.7 時間** | **8.6 時間** |

県を 4 つ足した時点では、実時間は逆に短くなっている。
地方県を毎日回すのをやめたぶんが浮いたため。
47 県へ広げても、**リクエスト頻度は 3 段階すべてで変わっていない**。
増えたのは実時間だけで、日次 cron の 24 時間に対してはまだ余裕がある。

## 3. 予算（budgetMin）の決め方

2026-08-07 の実測で、兵庫県は 63,309 件を 100 分/日で 7 日以内に一巡している。
ここから **毎分およそ 90 件**。県の在庫を Q 件として、7 日周期に必要な分数は

```
budgetMin ≒ Q ÷ 7 ÷ 90
```

既存 12 県の在庫は `src/data/areaDirections.json` の実測（2026-08-08）。

```
兵庫 63,309  大阪 61,546  広島 53,144  静岡 42,278  愛知 41,953  京都 36,732
三重 19,033  滋賀 16,140  奈良 12,753  鳥取  5,276  福井  4,544  島根  3,846
```

首都圏 4 県はまだ 1 件も取っていないので、市場規模からの見積もりを置いている。

| 県 | 見積在庫 | budgetMin |
|---|---|---|
| 東京 | 約 190,000 | 300 |
| 神奈川 | 約 100,000 | 160 |
| 埼玉 | 約 60,000 | 100 |
| 千葉 | 約 55,000 | 90 |

**初回の巡回が終わったら、`build_area_dataset.ts` が吐く実測値で置き直すこと。**
東京の在庫が見積もりより多ければ、300 分では 7 日に届かない。

## 4. 触るときの注意

### 4-1. 県のリストを他所に書かない

同じリストが以前は 5 箇所に散っていた。

```
scripts/nifty_extractor.ts              取りに行く県
scripts/purge_rental_properties.ts      範囲外として「消す」県
scripts/build_area_dataset.ts           エリアページを作る県
src/app/relocation/arbitrage/page.tsx   スキャナーの県プリセット
src/lib/guideContent.ts                 利用ガイドの説明文
```

**2 番目が他より狭いと、取り込んだ行がその晩のパージで消える。**
岐阜が実際にこの形で 0 件になっている。すべて `scrapeTargets.ts` から引く。

### 4-2. レジストリに依存を足さない

`scrapeTargets.ts` と `plan_scrape_matrix.ts` は import を持たない。
ワークフローの `plan` ジョブが `npm ci` を挟まずに `npx tsx` で読むため、
依存を足すとそこが壊れる。

### 4-3. 予算を増やしたらジョブの timeout も見る

`scrape` ジョブの `timeout-minutes` は 360。最長ジョブ（東京 300 分）に
対する余裕として置いてある。budgetMin をこれ以上に伸ばすなら一緒に上げる。

### 4-4. 巡回周期とパージの期限

`PURGE_STALE_DAYS` は 90 日。この日数だけ `last_seen_at` が更新されない行は
掲載終了とみなして消す。**一巡に 90 日以上かかる県を作ると、生きている物件を
消し始める。** 3 日に 1 回・60 分の三重で一巡およそ 11 日なので、いまは
8 倍の余裕がある。間隔をこれ以上延ばすときはこの計算をやり直すこと。

## 5. 47 県への拡張（実施済み）

残り 31 県を `SCRAPE_TARGETS` に足した。枠組みは変えていない。

### slug と座標をどこから採ったか

推測で書いていない。どちらも `public/prefectures.geojson` から導いている。

- **slug**: `name_english` を小文字にしたもの。
  **既存 16 県で 16/16 一致する**ことを確認したうえで残りに当てた
- **座標**: 県庁所在地。同じ geojson のポリゴンの範囲内に入ることを
  31 件すべて検算した

万一 slug が違っていても黙って 0 件にはならない。`nifty_extractor.ts` は
市区町村一覧が 3 回とも 0 件なら失敗する（`fail-fast: false` なので
その県のジョブだけが赤くなる）。

### budgetMin は仮の値

既存 12 県のような実測が無いので、人口規模の帯で置いた。

| 帯 | budgetMin | 例 |
|---|---|---|
| 200万人超 | 60 | 茨城・宮城・新潟・長野 |
| 100〜200万人 | 50 | 岐阜・群馬・岡山・熊本 ほか |
| 100万人未満 | 45 | 富山・香川・秋田・高知 ほか |

札幌と福岡だけ `metro`（毎日）にしてある。人口も賃貸在庫も既存 metro と
同規模で、3 日に 1 回では鮮度が保てないため。

**一巡したら実測値で置き直すこと。** 3 章の式で計算し直す。

### 律速は取り込みではなくジオコーディング

座標が付くまで、その物件は検索にもスキャナーにも出ない。
ジオコーダは町丁目単位のキャッシュで動いていて、2026-08-08 の実行では
**キャッシュ済み 15,669 町に対し GSI 問い合わせは 13 件**しか要らなかった。
新しい 31 県はこのキャッシュがまるごと無いので、埋まるまで数日〜2 週間かかる。

そのため `GEOCODE_TIME_BUDGET_MIN` を 60 → 150 に広げた。geocode ジョブの
`timeout-minutes` は 300 で、8/8 の実行は 18 分しか使っていない。

### 未対応: jis_city_codes.json が 12 県ぶんしかない

`scripts/jis_city_codes.json` は市区町村の正式名称と JIS コードの対照表で、
`build_area_dataset.ts` が住所から市区町村を切り出すのに使う。

| | 影響 |
|---|---|
| 地図の県別色分け・件数ラベル | **影響なし。** `listingCounts` は `PREF_JP` を使って県名で DB を直接数えている |
| 検索範囲の県プリセット | **12 県のまま** |
| `/houi/area/*` のエリアページ | **12 県のまま** |

e-Stat から取得して足す必要がある。

### これ以上広げるとき（あるいは budgetMin を実測で上げるとき）

決めるのは 1 つだけ。

**合計分数 ÷ 並列数 が 24 時間に収まるか。**

`plan_scrape_matrix.ts` はこれを毎回計算し、24 時間を超えると
ジョブごと落とす（黙って巡回が飛ぶより、気づける方がよい）。
20 時間を超えた時点で警告も出す。

収まらない場合の手は 3 つ。

1. `everyNDays` を延ばす — 鮮度が落ちる。4-4 の期限を必ず確認する
2. `budgetMin` を下げる — 同上
3. `SCRAPE_MAX_PARALLEL` を上げる — **相手サーバーへの負荷が比例して増える**

3 を選ぶときは、それが第三者のサーバーに直接かかる負荷であることを
意識して決めること。この値だけが負荷を決めている。

## 6. データの押し戻しとデプロイ（DATA_PUSH_KEY）

`geocode` ジョブの最後で `areaDirections.json` と `prefecturesWithData.json`
を master へコミットする。この 2 つは**ビルド時に静的に焼き込まれる**ので、
コミットしただけでは本番の表示は変わらない。デプロイまで届いて初めて変わる。

ところが長らく届いていなかった。原因が 2 つ重なっていた。

1. コミットメッセージの `[skip ci]`。push で動くワークフローは deploy.yml
   だけなので、飛ばしたい対象が無いのに唯一の対象を自分で消していた
2. **既定の `GITHUB_TOKEN` が押したコミットはワークフローを起動しない**

実際 `ded71b7` / `6df3e83` のデータコミットに対応するデプロイの実行は無い。

### いまの形

`[skip ci]` を外し、checkout をデプロイキー（SSH）で行う。

```yaml
- uses: actions/checkout@v4
  with:
    ssh-key: ${{ secrets.DATA_PUSH_KEY }}
```

PAT ではなくデプロイキーなのは**有効期限のため**。fine-grained PAT は
最長 366 日で切れ、切れるとこの checkout がその場で失敗して、パージも
重複排除もジオコーディングもエリア相場の再生成も丸ごと飛ぶ。
デプロイキーは無期限で、このリポジトリ 1 つにしか効かない。

### 鍵の作り方

秘密鍵は手元で作る。リポジトリには絶対に置かない。

```
ssh-keygen -t ed25519 -N "" -C "portfolio data push" -f data_push_key
```

- 公開鍵 `data_push_key.pub` → Settings > Deploy keys
  **「Allow write access」にチェックして**登録
- 秘密鍵 `data_push_key` → Settings > Secrets and variables > Actions
  `DATA_PUSH_KEY` として登録（`-----BEGIN` から `-----END OPENSSH PRIVATE KEY-----`
  まで、末尾の改行も含めて全文）

未設定でも壊れない。`GITHUB_TOKEN` に落ちて push 自体は通り、
デプロイだけが次の push 待ちになる。そのときはジョブのサマリーに
「`DATA_PUSH_KEY` が未設定」と警告が出る。

### この鍵でできてしまうこと

master への push は deploy.yml を起動し、deploy.yml は `ENV_FILE`
（`DATABASE_URL` / `DIRECT_URL` を含む）を渡してアプリをビルド・デプロイする。
つまりこの鍵が漏れると、**任意のコードを本番に載せて DB を読める**。
「公開リポジトリへの push 権限」だけの話ではないので、扱いは秘密鍵として扱う。
疑わしいときは Deploy keys から即座に削除すれば失効する。
