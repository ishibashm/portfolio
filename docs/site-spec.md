# Cloud Palette 仕様書

`cloud-palette.com` — 引越しの方位とタイミングを決めるサイト。

このファイルは「今どうなっているか」を書く。変更したらここも直す。
判断の経緯はコード中のコメントに書いてあるので、ここでは繰り返さない。

最終更新: 2026-10-17（初代案内役・しるべとAI相談の案内フローを追加）

---

## 1. このサイトが答える問い

```
どの方位へ動くか   九星気学の方位盤（年盤・月盤・日盤）で吉凶を出す
いつ動くか         六曜・天赦日・一粒万倍日・土用・天中殺を突き合わせる
どこに住むか       公的統計の家賃水準・空き家率と方位から街を比較する
```

この 3 つに関わらないものは置かない。かつては真太陽時・株価・技術トレンド・
X 閲覧・研究レポートが同居しており、17 ページ／47 API のうちナビから辿れるのは
8 件だった。中核と非中核の定義は `src/lib/siteStructure.ts` に 1 か所だけ置く。

## 2. ページ

### 中核（検索に出す・ナビに載せる・広告を出す）

`src/lib/siteStructure.ts` の `CORE_ROUTES` が唯一の定義元。ナビ
（`GlobalSidebar`）・`robots.ts`・サイトマップがすべてここを参照する。

`CORE_ROUTES` は**どこへ / いつ / いくら**の 3 群に分かれる
（`ROUTE_GROUPS` が群の唯一の定義元。ナビとホームがこれで並ぶ）。

| 群     | URL                     | 役割                       | 生成         |
| ------ | ----------------------- | -------------------------- | ------------ |
| —      | `/`                     | ホーム。盤とヒートマップ   | クライアント |
| どこへ | `/relocation/arbitrage` | 方位で街を探す             | クライアント |
| どこへ | `/relocation/simulator` | 引越し先を試算する         | クライアント |
| どこへ | `/relocation/wealth`    | 移住先の地域を比べる       | クライアント |
| どこへ | `/houi`                 | 本命星と吉方位を調べる     | ISR（60 秒） |
| いつ   | `/relocation/timing`    | 引越し時期を分析する       | クライアント |
| いつ   | `/calendar`             | 引越しの日取りを選ぶ       | 静的         |
| いつ   | `/relocation/dashboard` | 今日の方位と時刻を確かめる | クライアント |
| いくら | `/relocation/market`    | 家賃相場を分析する         | クライアント |
| いくら | `/relocation/purchase`  | 購入の相場を分析する       | クライアント |
| いくら | `/relocation/appraisal` | 検討中の物件を査定する     | クライアント |

`/news`（不動産・建築の情報を集める）は **2026-09-21 に閉じた。**他社の
RSS から見出しと要約の冒頭を取って並べる頁で、各社の RSS 利用規約を
こちらで確認できていないため（backlog 33 節）。同じ見出しを出していた
市区町村ページと県ページの欄も同時に外した。台帳（`data/newsSources`）は
残してあるので、規約を人が読んで確かめたら戻せる。

### 記事（操作せずに読める。検索の入口）

| URL                                | 枚数                     | 内容                                         |
| ---------------------------------- | ------------------------ | -------------------------------------------- |
| `/houi/{年}/{星}`                  | 年 × 9 星                | その年の吉方位・五黄殺・暗剣殺・歳破・本命殺 |
| `/houi/{年}/{星}/{月}`             | 年 × 9 星 × 12           | 月盤の同内容                                 |
| `/houi/area` `/houi/area/{コード}` | 市区町村ぶん             | その街の相場と、そこから見た方位             |
| `/houi/pref/{コード}`              | 47                       | 県内の相場と、県の重心から見た方位           |
| `/calendar/{年-月}`                | 18（今月から 17 か月先） | その月の「引越しに向く日」                   |
| `/guide` `/guide/{slug}`           | ガイド                   | 使い方と九星気学の説明                       |

パラメータ付きの頁は `generateStaticParams` で事前生成の候補を返す。
年星・月盤・市区町村・ガイドは `dynamicParams = true` とし、未知の値は
頁内の検証と `notFound()` で 404 にする。県・月別カレンダーも頁内で検証する。
市区町村は固有文のある頁だけ事前生成し、固有文のない既知の市区町村も
要求時に生成する。事前生成の一覧に無いことだけを理由に 404 にはしない。
`generateMetadata` で title・description・canonical をページ固有にする。

**月盤と月別カレンダーは別の索引方針。**`/houi/{年}/{星}/{月}` は
年・本命星・月の有限な組み合わせであり、日別 URL ではない。月盤は
`noindex, follow` としてサイトマップから除外する。
`/calendar/{年-月}` は自己 canonical の索引対象として維持する。

**市区町村ページは索引を絞る。**同一雛形だけの頁を大量に索引へ出さず、`AREA_EDITORIAL` に固有の
文章を書いた頁だけ `index` にする（#750〜。それ以外は noindex のまま
道具としては残す）。県ページは 47 県すべてに文章がある。
`next-sitemap.config.js` の一覧と食い違わないよう、`sitemapThinPages`
が突き合わせる。

**description も頁ごとに変える。**地名だけ差し替えた同じ 1 文を配ると、
索引から外した理由（地の文がどの URL でも同一）が meta に残る。
文章のある頁は 1 段落目から作る（`metaDescriptionFromIntro`）。

### 補助

`/about` `/contact` `/privacy` `/terms` `/login`

`/privacy` と `/contact` は AdSense の審査で見られるので消さない。
`/contact` と `/login` は noindex・サイトマップ非掲載。robots.txt では
塞がず、クローラーが noindex を取得できるようにする。

`/ask` は公開MCPを使って方位・日取り・街を複数ターンで相談する補助頁。過去の相談メモ、複数の保存会話、家族など複数人のプロフィールを扱う。`/houi` から控えめにリンクし、
CORE_ROUTES・主ナビには追加しない。入力後に結果が成立するため noindex, follow とし、
サイトマップから除外する。robots.txt では塞がない。

### 非中核

`NON_CORE_ROUTES` は `/relocation/history` と `/admin`。
`/relocation/history` は過去の移動から太極を出すページで、引越しの判断には
効くが導線からは外してある。`ADMIN_EMAIL` に一致する利用者だけが開ける。

`OFF_THEME_ROUTES` の `/relocation/yield` は投資家向けの道具として残す。
ログインは不要だが、ナビ・サイトマップから外し、robots.txt で巡回を制限する。
metadata は自己 canonical・noindex を明示する。ただし巡回制限下では
noindex が読み取られるとは限らず、これだけで索引からの削除を保証しない。

## 3. 方位の吉凶をどう決めるか

**ここがサイトの中心。ページによって違う判定・違う言葉を使わないこと。**

### 3.1 判定の本体

`src/utils/ephemerisEngine.ts` の `calculateVectorCollision` が唯一の判定器。
年盤・月盤・日盤と天中殺・月の交点・実行意図から、方位ごとの状態を返す。

```
yearLayer / monthLayer / dayLayer   盤ごとの状態
finalVectors                        3 つを合成した最終判定
```

合成には 2 系統ある。`actionIntent === "MIGRATION"` のときは年 → 月 → 日の順で
絶対格の凶を採り、日盤は `WARNING` に格下げする。それ以外（`DEFAULT` など）は
年月日を対等に合成する。**どちらが使われるかはページごとの `actionIntent` で
変わるので、新しい呼び出しを足すときは必ず明示すること。**

### 3.2 状態コードと日本語

日本語表記は `src/lib/directionLabels.ts` が唯一の対応表。**4 つの形を持つ。
言葉を変えるためではなく、置ける長さが違うために分けてある。**呼び名の系統は
4 つとも揃える（`short` と `detailed` は `name` で始まる。テストで固定してある）。

```
name      「五黄殺」        呼び名だけ。重さは別の列や色で出す
badge     「五黄」          地図の扇形に重ねる 1〜3 文字
short     「五黄殺 (大凶)」  文中に埋め込む
detailed  「五黄殺 (大凶 - 自己破壊のエネルギー)」  単独で説明する
```

以前は日取りパネル・地図の扇形・カレンダー・天地人・物件検索の API が
それぞれ手元の表を持ち、**同じ状態が画面をまたぐと別の名前**になっていた
（`NOISE_VOID` を「空亡」「ボイド」「天中殺方位」の 3 通りに呼んでいた）。
#570〜#573 で寄せた。**手元の表を作らないこと。**

| コード                               | 表記               | 意味                           |
| ------------------------------------ | ------------------ | ------------------------------ |
| `OPTIMAL`                            | 大吉方位           |                                |
| `OPTIMAL_REGULAR` / `OPTIMAL_BOOST`  | 吉方位             |                                |
| `SAFE`                               | **平穏**           | **凶方位ではない。吉ではない** |
| `WARNING`                            | 注意（引越当日）   | 長期は吉だが移動当日に干渉     |
| `NOISE_GOU`                          | 五黄殺             |                                |
| `NOISE_ANKEN`                        | 暗剣殺             |                                |
| `NOISE_HA`                           | 歳破 / 月破 / 日破 | **盤によって呼び名が変わる**   |
| `NOISE_HONMEI`                       | 本命殺             |                                |
| `NOISE_TEKI`                         | 本命的殺           |                                |
| `NOISE_VOID`                         | 天中殺方位         |                                |
| `NOISE_GETSUMEI` / `NOISE_GETSUTEKI` | 月命殺 / 月命的殺  |                                |
| `NOISE_NODE`                         | 羅睺・計都軸       |                                |
| `NOISE_TENCHU`                       | 天中殺             | 方位ではなく**期間**そのもの   |

`SAFE` を「吉」と書かないこと。判定の本体（`auspiciousDays.isAuspicious`）は
`OPTIMAL` 系だけを吉とする。以前は物件検索と資産マップだけ「吉方位」と出して
おり、同じ方位が記事では「平」になっていた。

`NOISE_HA` は盤で呼び名が変わる。`directionLabels.haLabelForLayer(layer)` を使う。

### 3.3 凶の重さ

`src/utils/noiseSeverity.ts` が唯一の定義元。

```
五大凶殺（移転で妥協しない）= 五黄殺・暗剣殺・破・本命殺・本命的殺
二次凶                      = 天中殺方位・月命殺・月命的殺・月交点
```

重い順は `NOISE_PRIORITY`。複数の凶が重なった方位を 1 語に畳むときは必ずこの順で
先勝ちにする。集合を自分のファイルに書き写さないこと（`isFatalNoise` を使う）。
凶かどうかの判定も `noiseSeverity.isNoise`。`auspiciousDays.isInauspicious` は
これを呼ぶだけで、**画面から呼ぶときは軽いほう**を使う（`auspiciousDays` は
判定エンジンを値として import しているので、client component から引くと
エンジンごとバンドルに乗る）。

**土用殺はこの表に無い。**年盤・月盤・日盤のどの層にも出ず、
`calculateVectorCollision` の最後で**最終だけを `NOISE_GOU` に上書き**する。
そのため三盤とも大吉なのに段階 X になる日があり、画面には「五黄殺」としか
出せなかった。#568 で `VectorCollision.doyouSatsuDirection` と
`DayVerdict.isDoyouSatsu` を足し、理由を持ち回れるようにしてある
（判定は変えていない）。**`NOISE_DOYOU` として切り出すのは未了。**
切り出すと `isFatalNoise` を外れて段階が X → D になるので、
`noiseSeverity` に「候補にしない集合」を先に置く必要がある。

### 3.4 段階と語彙

用途ごとに違う。**どれも定義元は 1 つずつ。自分のファイルに写さない。**

| 使う場面     | 段階                                      | 定義元                                                 |
| ------------ | ----------------------------------------- | ------------------------------------------------------ |
| 日付の格付け | S / A / B / C / D / X（三盤吉〜五大凶殺） | `utils/tierDisplay.ts` + `auspiciousDays.gradeVerdict` |

| 方位の評価 | 大吉 / 吉 / 平穏 / 注意 / 凶 / 大凶 | `lib/verdictRating.ts` |
| 合成した 0〜100 の点 | 大吉 / 吉 / 警告 / 大凶（80 / 50 / 30） | `lib/scoreTier.ts` |
| 記事の色分け | good / neutral / bad | `lib/kigakuContent.ts` |

**S（三盤吉）は「年・月・日が三つとも吉」。**#566 まではそうではなかった。
移転の最終判定は `criticalLayers = [年, 月]` しか見ないので、旧条件
（「最終が吉」＋「どの盤にも凶が無い」）は実質「年か月が吉」と同じ意味で、
**3 枚のうち 1 枚しか吉でない日まで S に数えていた**（実測で S 309 通りの
うち三盤とも吉は 14 通り）。同じ理由で A（吉2盤）は構造上 0 件だった。
`isTripleAuspicious` を三つとも吉に直して、ラベルが実態と一致した。

`verdictRating` は `isFatalNoise` から重さを引く。五大凶殺は必ず「大凶」、
二次凶は「凶」。以前はシミュレータと履歴が独自の表を持ち、本命殺を「凶」に、
天中殺方位を「大凶」に、と逆向きに重み付けしていた。

段階の色は `TIER_FILL`（発散型：吉は緑の濃淡 / 平は灰 / 凶は橙→赤）。
**色を変えたら検証が自動で回る。**以前ここには

```bash
node scripts/validate_palette.js "<6色>" --mode light
```

と書いてあったが、**このスクリプトはリポジトリに存在しない**（履歴を
遡っても無い）。規則はあるのに実行できない状態だったので、計算を
`src/lib/paletteChecks.ts` に置いて `__tests__/tierPaletteSeparation.test.ts`
から回すようにした。手で叩く必要はない。

見るのは**隣り合う段だけ**。段階には順序があるので、離れた段は元々別の色に
なっている。「大吉と吉が同じ色に見える」は常に隣どうしで起きる。

| 見るもの        | 下限 | なぜ                                                 |
| --------------- | ---- | ---------------------------------------------------- |
| 通常の視覚の ΔE | 15   | 文字ラベルの無い塗り（地図の扇形）で区別が付く最低限 |
| 色覚多様性の ΔE | 8    | 1 型・2 型を模した色の**悪いほう**で見る             |

ΔE は OKLab のユークリッド距離 ×100。色覚の模擬は Machado ほか (2009) の
重症度 1.0。**模擬の仕方と下限は対になっている**ので、行列を差し替えるなら
下限も測り直すこと。

`TIER_BORDER`（ピンの縁取り）は**いまも下限を割っている。**とくに
D（凶）と X（大凶）が ΔE 3.4 で、縁だけを見ると同じ色。縁は必ず塗りと
重なって描かれ塗りのほうは下限を満たしているので実害までは出ていないが、
「塗りだけ直すと縁とバッジが取り残される」の実例として残っている。
現状の数値はテストに固定してある。

以前は吉の 3 段が緑・青緑・水色と別の色相で、順序が色相の違いに化けていた。
S と A は実測 ΔE 5.4（下限 15）で、文字ラベルの無い塗り（地図の扇形）では
区別できなかった。塗りだけ直すとピンの縁とバッジが取り残される。
`TIER_BORDER` / `TIER_TEXT_CLASS` / `TIER_BG_CLASS` / `TIER_BADGE_CLASS` も
同時に揃えること。**ダークは不透明度だけで強弱を出す**（色相を混ぜると、
暗い地の上では明るい色ほど濃く見えて順序が壊れる）。

### 3.4.1 「今日は良い日か」は 2 つある

ホームと `/calendar` の日の点数（`widgets/CosmicCalendar`）は、
九星の判定とは**別体系**。統合していないので、名前で意味を分ける。

| 枠         | 中身                           | 誰にとっても同じか          |
| ---------- | ------------------------------ | --------------------------- |
| 暦の日取り | 六曜・天赦日・一粒万倍日・月相 | 同じ                        |
| あなたの日 | 天中殺・日破・支合             | 生年月日で変わる            |
| 方位の吉凶 | 三盤の段階（S〜X）             | 生年月日 **と出発地**が要る |

3 つ目はこの画面では出さず、`/relocation/timing` へ送る。

**西洋占星術の要素を判定に混ぜない。**水星・金星・火星の逆行が日の点数を
最大 22 点下げていた。逆行の表示自体は参考として残してあるが、
「日の点数には使っていません」と画面に書くこと。

### 3.5 絞り込み

`filterCollisionByMode(collision, …, directionFilterMode, …)` を必ず通す。
`"composite"` は素通しなので、既定でも呼んで構わない。通し忘れると、
利用者が選んだ絞り込みだけが効かないページができる。

### 4.0 六十干支と二十四節気の表示

`lib/kanshi` が年月日の干支・日柱由来の空亡・二十四節気の時刻を提供する。
年は立春の瞬間（既存の `honmeiYearFor`）、月は12の節入り（既存の太陽黄経と
`getSolarMonthIndex`）、日はJST0時（既存の `calculateTenchusatsu`）で切り替える。
出生地の真太陽時補正は行わない。九星・方位の既存判定には混ぜない。

二十四節気は既存の `AstroEngine.getSolarLongitude` の15度ごとの通過時刻を
求める。JSTの計算値として表示し、公式暦との差を明記する。国立天文台の
2026年全24節気と2025年立春・立冬の暦要項で、差が3分以内であることをテストする。
月を切り替える12の節と、月を切り替えない12の中気を区別して表示する。

日付だけの出生は正午を代表値とし、節入り当日は前後の柱も併記する。
日時が明示された出生はその瞬間を使う。本命星早見、暦の選択日、月別暦に表示。
公開MCP `get_kanshi` は1900〜2100年の出生を受け、各柱と年干支が一致する節年を
出生暦年から120年後まで列挙する。時刻不明の境界日は併臨年も両候補を返す。
空亡・干支併臨から出来事を予言しない。空亡は方位凶殺とは別体系。

`get_honmei_star` と `find_auspicious_days` は既存項目を維持し、干支・節気情報だけを
追加する。旧ツールの対応範囲外の出生は追加干支がnull、範囲外の節気は一覧に含めない。

### 4.1 時刻はすべて日本時間の正午に寄せる

`Date` のローカルのゲッター／セッター（`getFullYear` / `setHours` / `getDay`）は
**実行環境のタイムゾーンで動く**。本番（Cloud Run）は UTC、ブラウザは JST なので、
使うと同じ日が別の意味になる。日取りの経路では次を守る。

```
評価する時刻   forecastAnchorMs(d)   その日の日本時間の正午
YYYY-MM-DD     日本時間基準で組む     getFullYear を使わない
曜日           日本時間基準で組む     getDay を使わない
1 日進める     ミリ秒を足す           setDate を使わない
```

実害の記録。`setHours(12)` を使っていたため、サーバ側の判定だけが
**21 時 JST の盤**を見ていた（#563。立春でいうと 1950〜2050 年の 101 年のうち
34 年で年盤の星が食い違い、本命星 9 × 8 方位 = 7,272 通りのうち 1,930 通りが
別の判定になった）。天中殺の干支だけ 9 時 JST で引いていた例もある（#564）。

`Solar.fromDate` は**使わない**（同じ理由。`getZonedDateTimeFields(date, 9)` を
通して `Solar.fromYmdHms` で組む）。

`CHAIN_TOOLS`（lib/mcpChain）を唯一のallowlistとする。登録一覧との照合テストで

```
CI（.github/workflows/ci.yml）  PR ごとに tsc / lint / vitest
デプロイ                        master への push で Cloud Run へ
```

CI では `next build` を回さない。ビルドは `.env`（DB 接続文字列を含む）を
前提にしており、PR の実行に渡すと公開リポジトリで秘密情報を晒す。

`npm ci` は旗なしで通る。以前は `defuddle@0.8.0` が `jsdom@^24` を要求して
`--legacy-peer-deps` が要ったが、`defuddle` を 0.19 に上げ、`react-simple-maps` の
react の peer は `package.json` の `overrides` で揃えた（2026-10-08）。
Node は Dockerfile と同じ 20 に固定する。

lint の警告は落とさない（現在 509 件）。止まるのは error だけ。
以前、lint が赤いまま直らず CI ごと削除された経緯がある。
**PR の前後で総数が増えていないことを毎回確かめる。**自分が足したテストで
増やす事故が実際に何度も起きている。

### 本番の画面を見る

`node scripts/verify_production_ui.mjs`

**CI が緑でも、本番を開くまで分からない不具合がある。**実際に 2 回出した。

どちらも HTTP は 200 で、tsc もテストも通っていた。デプロイのたびに
このスクリプトを走らせること。項目を足すときは、**壊れている状態で NG に

### 日本語の文中に半角スペースを入れない

`__tests__/jsxJapaneseLinebreak.test.ts`（`scripts/find_jsx_ja_linebreaks.mjs`）

JSX はテキストノードの改行を半角スペース 1 つに変換する。英語では単語の
区切りとして正しいが、**日本語では文が割れる。**

```jsx
// ソース                          // 画面
<p>
  {" "}
  この方位には現在の検索範囲に物件が この方位には現在の検索範囲に物件が
  ありません。 ありません。 ↑ ここに空白が入る
</p>
```

読みやすく折り返しただけのつもりが、そのまま表示に出る。書いた本人が
気付きにくく、**144 か所 / 28 ファイル**まで溜まっていた（#183〜#195 で全部消した）。

直し方は**行を連結するだけ**。prettier は日本語テキストを再分割しない
（区切る空白が無いため）ので、連結しておけば整形で元に戻らない。

見るのは**両側が日本語のときだけ**。日本語と数字の境目は含めない
（「掲載中の 1,234 件」のように意図して空けている箇所がある）。

## 10. 触るときに気をつけること

- **同じことを 2 か所に書かない。**このサイトの不具合の多くがこれで起きている。
  凶の集合・方位の日本語・非中核ルート・6 段階の畳み方は、どれも過去に
  写しが増えて食い違った
- **`SAFE` は吉ではない**
- **`toISOString()` で日付を切らない。**サーバは UTC
- **Leaflet はマーカーを緯度順に並べ替える。**DOM の順番は作った順ではない
- **日本語は `min-content` が 1 文字。**flexbox の `min-width:auto` では守れず、
  兄弟に `shrink-0` があると 1 文字ずつ折り返す
- **`next/font` は CJK の全サブセットを preload する。**`preload: false` にする
- **推測で断定しない。**実測してから報告する

### Grok 音声モード（2026-10）

`/houi/mcp-explorer` とホームから開く既存チャットに、押して話すマイクを追加。
音声クライアントは遅延読み込みし、ホームの入口の初期JSには含めない。
マイクボタンを押す／フォーカスしてスペースキーを押し続け、離して送信する。
初回はマイク許可・接続準備が必要。拒否・非対応はテキスト入力を案内する。
利用者とGrokの確定文字起こしを画面に表示し、道具の経緯は既存の折りたたみに表示。
保存済みプロフィールは音声へ自動追加しない。終了・画面離脱・設定削除時にマイクと接続を解放する。

`XAI_API_KEY` と `MCP_VOICE_ENABLED=true` の両方で有効。
開発時のみ `MCP_VOICE_MOCK=true` で鍵・マイク・xAI接続なしの固定例を使用できる。
モックも `/api/voice/tool` と本物のin-process MCPを通し、応答をブラウザの音声合成で再生する。
本番モデルは `grok-voice-3.0` に固定し `XAI_VOICE_MODEL` で変更する。

- `POST /api/voice/session` は既存Origin検査・`canUseAgent` の無料枠、IP/全体バケットを通す。
  JST日次音声上限（全体 `MCP_VOICE_DAILY_SECONDS=1800`、利用者 `MCP_VOICE_FREE_DAILY_SECONDS=180`）と
  `MCP_VOICE_MAX_SESSION_SECONDS=180` の最小秒数を、外部I/Oの前に台帳で予約する。
  xAI `POST /v1/realtime/client_secrets` に `expires_after.seconds` を渡す。
  応答は短命token・expires_at・署名付きsessionId・model・9道具のfunction定義・instructions。
  API鍵はサーバーだけで保持。署名鍵は API_SECRET_KEY → NEXTAUTH_SECRET → XAI_API_KEY の順で選び、用途をHMAC入力で分離する。
- ブラウザは `wss://api.x.ai/v1/realtime?model=...` に `xai-client-secret.<token>` のsubprotocolで接続。
  `session.update` は eve、手動turn_detection=null、PCM16/24kHz、language_hint=ja。
  押下中だけ送信し、離すとcommitとresponse.createを送る。
- `POST /api/voice/tool` は署名・保存済みセッション・期限・allowlistを確認。
  セッション当たり最大20回（`MCP_VOICE_MAX_TOOL_CALLS` で縮小可能）、1回8秒、出力6000文字。
  call_id再送は拒否し、並列呼び出しもawait前に回数を消費する。
  出力はUNTRUSTED_TOOL_DATAで囲み、テキスト版と同じ注入対策を共有する。
  response.doneで並列呼び出しの組を確定し、全結果を返してからresponse.createを送る。
- `POST /api/voice/end` は申告秒数を予約秒数までに丸め、二重精算せずUsageLedgerのvoiceSecondsへ記録。
  終了通知が無いセッションは次のAPI要求時に期限を確認して全量消費として確定する。
  発行失敗が外部サービスで成功した可能性もあるため、失敗時も予約は保守的に消費する。
  音声・文字起こし・道具入力・生年月日・トークンはサーバーログへ記録せず、エラーは定型文のみ。

台帳とセッションは既存AI同様インスタンス内メモリ。再起動で消え、複数インスタンスでは日次枠は共有されない。
別インスタンスに届いたtool/endは安全側に拒否するため、複数台運用には共有ストア／ルーティング対応が必要。
短命tokenの期限は認証の期限であり、接続中の課金時間の強制遮断を保証しない。
クライアントのタイマーと申告精算は改変可能であり、厳密な費用制御にはサーバー中継と共有台帳が必要。

Realtimeがfunction呼び出しに対応するため、STT→テキスト→TTSの代替経路は作らない。
xAIのmcp型は実行がサーバー外となり上限・台帳を通せないため使わない。
料金は利用者確認の2026-10仕様でSpeech to Speech $0.08/分、STT $0.10/時、TTS $15/100万文字。
プロトコル参照：[xAI Speech to Speech](https://docs.x.ai/developers/model-capabilities/audio/speech-to-speech)、
[イベント仕様](https://docs.x.ai/developers/rest-api-reference/inference/voice)。
AIチャットの補足（2026-10-17）:

- 「方位と住まいの手帖 by cloud-palette」の初代案内役は「しるべ」。落ち着いて親しみがあり、方位と住まいに詳しい若い男性の案内役で、一人称は「私」、丁寧な「です・ます」調で温かく簡潔に話す。AIのsystem promptもこの人格を指定する。チャットの顔写真には公式キャラクター素材の `public/guide/shirube-pointing-{96,240}.{avif,webp}` だけを使い、AVIF→WebPの`picture`、明示した縦横寸法、CSSの顔位置で丸く切り抜く。
- 空の会話では、しるべが最初に話す。登録済み人物のクイック返信、人物情報なし、新しい人物の登録から選び、新規登録は呼び名、生年月日、任意の出生地、任意の現住市区町村を会話内の小さな入力で順に聞く。その後、引越し方位、日取り、街探し等の相談候補と自由入力へ進む。登録済み人物がある再訪時も、短い挨拶と人物選択から始める。この案内ステップはクライアント内だけで動き、送信ボタンを押すまで `/api/mcp-chain` を呼ばず、AI無料枠も消費しない。
- 空の会話に出す相談候補は、選択人物の実際の呼び名、生年月日、現住所だけから作る。値が無ければ日付・地名を含まない汎用候補にする。架空の生年月日や市区町村を例として補わない。
- `/ask` は発言をメッセンジャー型のスレッドで表示し、案内フローとAI回答はいずれもしるべを左側、利用者をアバターなしの右側に置く。しるべの全吹き出しに32px（モバイル）／40px（`sm`以上）の顔を添え、連続するしるべ発言では最初の吹き出しだけに小さく「しるべ」と表示する。回答中も本文を逐次表示する。入力欄は画面下にsticky配置し、Enterで送信、Shift+Enterで改行、IME変換中のEnterは送信しない。AI方式では会話、最新回答、使った道具と結果、選択人物、相談メモを踏まえた追質問候補を、最終回答と同じモデル生成の非表示JSONから `done.suggestions` として2〜4件返す。追質問だけの別モデル呼び出しと別の台帳予約は行わない。計算のみ方式は、街・吉方位・候補日など実際の道具結果から決定的に候補を作る。
- 追質問候補はサーバーとクライアントの両方で、2〜4件、各60文字以内、日本語を含む平文として検証する。空白を整え、重複を除き、Markdown・HTML・URL・制御文字を含む項目を捨てる。欠落・不正・2件未満なら従来の質問キーワード別 `followUps()` に戻す。
- 候補チップは押しただけでは送信せず、入力欄へ入れてフォーカスする。人物や相談メモから引き継いだ前提を利用者が送信前に確認・編集でき、意図しないAI枠の消費も避けられるため。計算のみ方式でも同じく入力欄へ入れる。
- APIへは現在の質問と直前の会話を別フィールドで送り、モデルにもuser/assistantの順で渡す。新しいチャットでは履歴を送らない。各POSTは従来どおり無料枠を1回予約し、台帳に質問や履歴は書かない。
- 相談メモと複数人物を追加しても、課金台帳の予約・完了・残数ヘッダは同じ1回の`/api/mcp-chain`実行に対して従来どおり動く。メモ作成のための別の生成APIは呼ばない。計算のみモードは従来の決定的連鎖を1人ずつ実行する。
- `done` の呼び出し数をそのまま本文末へ出さない。回答ごとに「確認に使った道具」を折り畳み、0件も利用者向けの説明にする。決定的方式も「計算に使った道具」として折り畳む。
- 月日を推測してbirthDateに入れない。エージェントの道具実行時に、現在の質問・過去の利用者発言・相談プロフィールの西暦・和暦・月日だけの表記を正規化して照合する。不一致は「月日が不明です。年だけの入力を使うか利用者に尋ねてください」をモデルへ返す。外部MCPのbirthDate入力は従来どおり。
- get_honmei_starはbirthYear（1900〜2100）と任意のbornBeforeSetsubunを受ける。省略時は前年・当年の両候補。1/1〜2/4は立春前後の確認が必要で、境界日には実際の節入り時刻で分かれる。年だけの結果から日柱・空亡は出さない。
- 残回数は個人回数・全体回数・個人トークン・全体トークンの残枠のmin。予約は実行中に1回、完了時は予約を台帳に移して二重計上しない。GET /api/mcp-chain/statusも同じIP識別・計算を使い、照会では予約もレートも消費しない。POSTヘッダは当該実行を予約した後の残数。
- 以前の「20回設定なのに残り2回」は固定の個人トークン既定値1572864が3回相当に制限したため。未指定のトークン枠は回数に連動するよう変更した。明示したトークン枠は引き続き優先される（例:1572864なら3回）。個人20回でも全体を他の利用者が消費すれば残数は減る。
- 日次クォータは再試行せず `MCP_AGENT_FALLBACK_MODEL`（既定gemini-3.5-flash-lite、空文字または主モデルと同じなら無効）へ切り替える。取得済み結果がある場合は道具を再実行せず、その結果から道具なしの最終要約を生成する。結果取得前の短い429/503は500ms、1000msの再試行後に切り替える。完了済み会話と道具の実行キャッシュは保持する。台帳modelは最後に実際に呼んだモデル。
- 全体60秒のうち約10秒を最終要約用に確保する。ステップ・道具回数・時間上限、空回答、取得後のモデルエラーで本文がなければ、同じsystem指示とUNTRUSTED_TOOL_DATAで取得済み結果を包み、道具なしの要約を1回生成する。429/503/日次枠ならフォールバックを使用する。要約も失敗した場合はサーバーが検証済みの市区町村・本命星候補・吉日・記事等から決定的な日本語平文を送る。利用者による切断を除き本文なしで終了しない。
- 個人の既定枠は30実行/日、全体は100実行/日。トークン枠は従来どおり回数×524288で算出し、環境変数の明示値を優先する。プロバイダーのgenerateContent枠とは別で、1実行に複数のモデル要求を使う。
- 成功・例外・中断・切断・時間上限のfinallyで予約と同時実行数を解放し、transportのclose完了を待たない。短時間のレート制限は「実行中」と区別する。
- deploy.ymlでは回数・トークン・フォールバックをGitHub Variablesから渡す。GitHubで空と未設定を区別できないため、フォールバック無効化にはMCP_AGENT_FALLBACK_DISABLED=trueを設定する。ローカル設定例は.env.local.example（このリポジトリの.env.example相当）。
- 2026-10-16 時点の運用: 主モデルは無料枠の `gemini-3.5-flash`（repo 変数 `MCP_AGENT_MODEL`）。この鍵では `gemini-4-argon`・Pro 系は無料枠 0 で 429、3.7/3.8-flash は高負荷で 503 が出た。無料枠には分あたり・日あたりの回数上限があり、混雑時は 429/503 になる。

### AIに聞く・回答ブロック

利用者向けの名前は「AIに聞く」。`/ask` は noindex としサイトマップから除外。旧 `/houi/mcp-explorer` は `/ask` へ恒久リダイレクトする。API は `/api/mcp-chain` を維持。

回答は短い安全な Markdown と、共通 zod スキーマで検証する `compass` / `towns` / `days` / `rentTable` / `articles` / `callout` / `text` ブロック。HTMLは実行しない。数値はサーバーの道具出力からそのまま転記し、欠損値を補完しない。エージェント専用 `show_blocks` はブロック種別・実行済み呼び出しID・短い注意文だけを受け取る。未知IDは拒否し、公開MCPには登録しない。選択に加えて道具結果から既定ブロックを表示し、同じ種類・同じ内容のブロックは回答全体で一度だけ表示する。`blocks` NDJSONイベントはクライアントでもブロックごとに再検証し、不正な項目を捨てる。決定的モードとホームの遅延読み込みチャットも共通表示を使う。

- 街候補はarea_directionsを方位別にまとめ、judge_directionsの大吉・吉（OPTIMAL/OPTIMAL_REGULAR/OPTIMAL_BOOST）だけを既定表示。未判定・平穏・凶は表示しない。1方位6件・合計18件まで、残件数は道具のcountから算出し「この方位の街をもっと見る」で出発地の既存/houi/areaページへ移動する。家賃nullは欄を省略、空の家賃表を作らず、カードの県名は一度だけ表示する。
- 依存のない道具は同じモデルステップで並列実行する。1ステップはモデル呼び出し1回（再試行は別途）。通常最大8ステップ、再試行・フォールバックも完了ステップの残枠を共有する。system promptで結果の再利用、必要時のみ記事検索、要約で足りる場合の記事本文取得省略、自動表示で足りる場合のshow_blocks省略を指示する。
