## 3. 九星気学についての整理（実装ではなく前提の共有）

「東へ凶方位で移動 → 75 日 → 吉方位へ移動」で、最初の凶は相殺されるのか、という問い。

**流派で言うことが違う領域なので、サイトとして断定的に書かない。**
確実に言えるのは幾何のほうだけ。

### 第 2 移動が短いと、元の起点から見た方位は変わらない

京都を起点に計算した実測値。

```
東  30km → 南東  10km : 元の起点から E   ← まだ東の扇形の中
東  80km → 南東  30km : 元の起点から E   ← 同上
東 200km → 南東  80km : 元の起点から E   ← 同上
東  80km → 南東  80km : 元の起点から SE
東  10km → 南東  10km : 元の起点から SE
```

目安として、**第 2 移動が第 1 移動の半分ほどないと扇形を出ない**（45 度ずらす場合）。

**2026-08-27 追記 — 「1.5 倍程度」と書いてあったのは誤り。**上の実例は
どれも正しいが、そこから読み取った目安の数字が実測と合っていなかった。
判定エンジンの方位計算で閾値そのものを走査すると、東へ 100km 動いた
あと南東へ動く場合、**53km（0.53 倍）**で扇形を出る。上の実例が
0.40 倍で「出ない」・1.00 倍で「出る」なのと矛盾しない。1.5 倍は
その区間の外側にあり、必要な距離を 3 倍近く過大に見せていた。

必要な比は 2 回目の向きで変わる（1 回目に東へ 100km の場合）。

| 2 回目の向き | 出るのに要る距離 |
|---|---|
| 南東（45 度ずらす） | 53km |
| 南南東 | 33km |
| 南（直角） | 27km |
| 東（同じ向き） | **どれだけ進んでも出ない** |

扇形の幅でも変わる。四正（東西南北）は 30 度なので直角に 27%、
四隅（北東など）は 60 度なので 58% 要る。**四隅のほうが倍のスケールが
要る。**この実測は記事
`content/blog/honmeisatsu-year-board-next-move.md` に載せた。

75 日で基点が移る規則（実装済み）は「**次の移動をどこから測るか**」を決めるだけで、
「元の起点から見てどこにいるか」は別の話。ここを混同すると、
「吉方位へ動いたはずが、元の起点から見るとまだ凶方位の中」が起こる。

### 画面に出すとしたら

**提案：シミュレータで「元の起点から見た現在地の方位」を併記する。**
基点は移っても、元の起点からの方位は消えないという事実だけを示す。
相殺されるかどうかの解釈には踏み込まない。

これなら流派の判断をサイトが下さずに済み、利用者は自分の流派で解釈できる。

## 8. `finalVectors` の型が八方位しか埋めていないのに CENTER を約束している

`calculateVectorCollision` / `filterCollisionByMode` の戻り値は
`finalVectors: Record<Direction, VectorStatus>` を名乗っている。ところが

#536 で判定の型を整理したとき、`Record<Exclude<Direction, "CENTER">, …>`
に直そうとしたら、`Direction` で回して添字を引いている呼び出し側が
一斉に落ちた。**落ちた場所はどれも、実行時に `undefined` を掴みうる

を引数に持っている。`VectorCollision` に寄せれば一緒に消える。

### なぜ #536 で直さなかったか

z=10〜12 の広い bbox、あるいは県か半径を指定した状態——は毎回走査する。

しかも前回の一致件数が上限 500 を超えていると（写真は 11,457 件）、
`lastTotal <= dataLimit` が偽になり**範囲を動かすたびに再走査**になる。
これは正しい（上限に当たった窓は広い範囲の上位 500 なので、狭めた範囲の
上位 500 とは限らない）。

### 遅い理由は SQL の形

    innerSql:  SELECT DISTINCT ON (name_key, floor, layout, size_sqm, rent) …
               ORDER BY <名寄せ鍵>, <代表行の選び方>
    selectSql: … ORDER BY percent_rank() OVER (ORDER BY sqm_rent) * 0.4 + …
               LIMIT 500

`DISTINCT ON` と `percent_rank() OVER` は、**bbox 内の全行を実体化して
ソートしてからでないと LIMIT を掛けられない。**俯瞰で bbox が広がるほど
行数に比例して遅くなる。並行して同じ行を `uniqueCountSql` が GROUP BY で
もう 1 回数える。work_mem を広げても速くならなかった（#296。律速は CPU）。

描画側は原因ではない。ピンは画面内だけ（`pinProperties`）、まとまりも
`visibleCount <= 100` のときだけ作る。

### 直すなら（判断待ち）

1. **bbox の面積で止める。**いまは県／半径の有無で判定しているが、
   遅さは面積で決まる。一定以上の面積では走査せず、県別・表示範囲の
   件数（`prefecture-counts` / `viewport-count`。どちらも索引の範囲引きで
   軽い）だけを出す。**「遅い」が「出ない」に変わる**ので利用者の判断が要る
2. **並び順の窓関数を LIMIT の後に回す**（先に sqm_rent だけで上位 N を
   取り、その中で 4 軸の percent_rank を出す）。答えが少し変わる
   （3 節の手順が要る）
3. 本番の EXPLAIN を取る。`db-explain.yml` が `prefecture=all` の最悪
   ケースを流せる。**本番 DB に数十秒の負荷を掛ける操作**なので投入は
   聞いてから

### 教訓

- **probe は 1 回で終わらない。**一覧ページの zip は 0 本（絶対パス

  無いと 404**。新しいワークフローは 1 度マージしてから枝で回す
