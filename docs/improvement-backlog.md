## 3. 九星気学についての整理（実装ではなく前提の共有）

「東へ凶方位で移動 → 75 日 → 吉方位へ移動」で、最初の凶は相殺されるのか、という問い。

**流派で言うことが違う領域なので、サイトとして断定的に書かない。**
確実に言えるのは幾何のほうだけ。

### 第 2 移動が短いと、元の起点から見た方位は変わらない

京都を起点に計算した実測値。

```
東  30km → 南東  10km : 元の起点から E   ← まだ東の扇形の中
東  80km → 南東  30km : 元の起点から E   ← 同上
東 200km → 南東  80km : 元の起点から E   ← 同上
東  80km → 南東  80km : 元の起点から SE
東  10km → 南東  10km : 元の起点から SE
```

目安として、**第 2 移動が第 1 移動の 1.5 倍程度ないと扇形を出ない。**

75 日で基点が移る規則（実装済み）は「**次の移動をどこから測るか**」を決めるだけで、
「元の起点から見てどこにいるか」は別の話。ここを混同すると、
「吉方位へ動いたはずが、元の起点から見るとまだ凶方位の中」が起こる。

### 画面に出すとしたら

**提案：シミュレータで「元の起点から見た現在地の方位」を併記する。**
基点は移っても、元の起点からの方位は消えないという事実だけを示す。
相殺されるかどうかの解釈には踏み込まない。

これなら流派の判断をサイトが下さずに済み、利用者は自分の流派で解釈できる。

### コード側で潰した疑い（すべて原因ではない）

| 疑い | 確かめ方と結果 |
| --- | --- |
| サイトマップの中身 | 正常。index → `sitemap-0.xml`、**813 URL**、130KB |
| ビルドで生成されない | 生成される。`.dockerignore` も `public/sitemap*.xml` を除外していない |
| イメージに入らない | Dockerfile が `COPY --from=builder /app/public ./public`。standalone の公式手順どおり |
| `next.config` の転送・書き換え | `/sitemap.xml` に触るものは無い（`www` → apex の 301 のみ） |
| `robots.txt` で塞いでいる | 塞いでいるのは `/admin`・`/api`・`/relocation/history` だけ |
| canonical が無い | `/admin/metrics`（意図的に noindex）以外**全ページにある** |
| 量産ページの題名が重複 | 年・星ごとに固有（`2026年 一白水星の吉方位と凶方位`） |
| サイトマップに認証・管理系が混入 | 0 件。813 件すべて公開ページ |

**ブラウザで `https://cloud-palette.com/sitemap.xml` を開くと正常に XML が返る**ことを
利用者が確認済み（2026-08-13）。**ファイルは本番に存在し、200 で配信されている。**

### 訂正 — #258 の説明は誤りだった

#258「サイトマップに認証を掛けていたのをやめる」の本文に

> `/sitemap.xml` を取りに来ただけで updateSession が走り、1 回ごとに
> Supabase の getUser() へネットワーク往復が入る

と書いたが、**これは誤り。**`utils/supabase/middleware.ts` には既に番人がある。

```ts
// On public routes without auth cookies, skip remote auth network call
if (!requiresAuthentication && !isLoginPage && !hasAuthCookie) {
  return supabaseResponse;
}
```

クローラは Cookie を持たず `/sitemap.xml` は保護対象でもないので、**往復は起きていない。**
#258 の変更自体（公開ファイルに middleware を通さない）は妥当だが、**取得失敗の
原因の説明にはなっていない。**同じ勘違いを繰り返さないため、番人の存在をここに残す。

### 残っている有力な原因 — コールドスタート

```
--min-instances=0   ← 待機インスタンスなし。途切れると毎回起動から
--memory=512Mi
--cpu=1
```

Google が取りに来たときにコンテナが停止していれば**起動から始まる**。Next.js
standalone ＋ Prisma を 512Mi で立ち上げるので初回応答が遅く、取得が失敗と

## 8. 管理画面の運用経費

「必要になっている経費も表示したい」への対応。**3 段構えで、利用者の指示は「全部」。**

| 段 | 中身 | 状態 | 手作業になる部分 |
| --- | --- | --- | --- |
| 1/3 | 固定費（手で維持する表） | **完了（#257）** | なし |
| 2/3 | 外部 API の従量（呼び出し回数 × 単価） | 未着手 | **新しいテーブルの DDL 適用** |
| 3/3 | GCP の請求 API から実額 | 未着手 | **Billing 権限のサービスアカウントと Secret 登録** |

### 金額の扱い（#257 で決めたこと）

**推測の額を入れない。**分からないものは `null`（未設定）にして画面にもそう出す。
もっともらしい額を置くと、あとから見た人がそれを実額だと思い込む。#231 で
存在しない項目を読んで NaN を出していたのと同じ筋。

- **一部だけ埋まった状態では合計を出さない。**足すと実際より小さい額が「合計」として
  出る。経費は割に合うかを判断する数字なので、小さく出るのが一番まずい
- **0 円と未設定は別物。**無料枠に収まって 0 円は確かめた事実、未設定は調べていない
- 単価は分母が 0 なら出さない（登録者 0 人で Infinity や NaN を出さない）

### 埋めてもらう必要があるもの

`src/lib/operatingCosts.ts` の `monthlyYen`。**5 件とも未設定のまま。**

```
cloud_run / supabase / domain / artifact_registry / external_api
```
