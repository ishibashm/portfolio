## 1. すぐ着手してよいもの

判定ロジックに触らない。`CLAUDE.md` の「やってよいこと」の範囲。

### A. 俯瞰が黙って別の意味の色に落ちるのを直す

**優先度：高。**いま一番実害が大きい。

出発地か生年月日が入っていないと、県の塗り分けが「方位の吉凶」から「掲載件数」へ**無言で切り替わる**。
どちらも同じ場所を色で塗るので、利用者は**件数の色を吉凶だと誤読する**。

やること。

- `prefKigaku` が undefined のとき、俯瞰の凡例に「生年月日と出発地を入れると方位の吉凶で塗り分けます」と出す
- 件数モードで表示していることが分かる見出しを凡例に付ける（今は色バーに「件数」とだけ）
- 切り替えボタンの「方位の吉凶」を、条件を満たさないときは disabled にして理由を出す

触るファイル：`src/components/ArbitrageMapInner.tsx`（＋必要なら `arbitrage/page.tsx` から条件を渡す）

**受け入れ条件**

- 生年月日が空のまま俯瞰にしても、色が何を意味しているか画面から分かる
- 判定・色の計算そのものは変えない

---

### B. 時期ヒートマップに段階フィルターを付ける

利用者の要望そのもの。段階は既に計算済みなので、表示を絞るだけ。

対象：`src/app/relocation/timing/page.tsx` のカレンダーヒートマップ（625 行あたり）

```
三盤吉 / 吉2盤・凶なし / 吉1盤・凶なし / 凶なし（平） /
軽い凶のみ / 五大凶殺あり / 天中殺
```

**注意：「天赦日・一粒万倍日」は軸が違う。**
上の 7 つは方位の吉凶（`DayTier` + `blocked`）だが、天赦日・一粒万倍日は**日の暦注**で、
方位とは独立に決まる。同じ選択肢に混ぜると「S かつ天赦日」が表現できない。
**別トグル（AND で重ねる）**にすること。

**受け入れ条件**

- 段階を複数選べる。既定は全選択（＝今と同じ見た目）
- 暦注トグルは段階フィルターと AND で効く
- 絞った結果 0 件の日は「該当なし」と分かる（空白と区別できる）
- 判定・段階の割り当ては変えない

### C. 物件検索に吉凶の分布を出す

「物件を方位で探す」で全体像が掴めない、という指摘。

**提案：方位別（8 方位）× 段階の積み上げ棒。**
「南東に S が 12 件」が一目で分かる形。単純な段階別ヒストグラムより、
この画面の目的（どっちへ動くか決める）に合う。

- 色は `utils/tierDisplay.TIER_FILL` を使う。**新しい色表を作らない**
- 棒をクリックしたらその方位＋段階で一覧を絞れると尚よい

触るファイル：`src/app/relocation/arbitrage/page.tsx` ＋ 新規コンポーネント 1 つ

> グラフを描く前に `dataviz` スキルを読むこと。

### D. 暦カレンダーの重複を解く

いま 2 つの実装がある。

| 実装                                          | 使われている場所                                    |
| --------------------------------------------- | --------------------------------------------------- |
| `widgets/CosmicCalendar.tsx`                  | `/calendar`、ホーム（`SolarTimeClock` から 2 箇所） |
| `relocation/timing/page.tsx` の独自カレンダー | 引越しの日取りを選ぶ                                |

**提案：役割で割る。**

- **ホーム** — 「今日はどうか」だけ。月カレンダーは置かず、今日の詳細と `/calendar` への導線
- **`/calendar`** — 暦そのものを見るページ。`CosmicCalendar` はここが本籍
- **引越しの日取り** — 「いつ動くか」を決めるページ。方位 × 日のヒートマップが主役で、暦の詳細は `/calendar` に譲る

同じ月カレンダーが 3 か所にあると、どれが正なのか分からなくなる。
`docs/site-spec.md` の「同じことを 2 か所に書かない」と同じ話。

**この項目は見た目が変わる。**着手前に相談すること。

### E. 距離を評価に入れる

**指摘は正しい。**現状 `scoreProximity` は「近いほど高得点」という**通勤利便性の指標**であって、
方位の作用の強弱とは無関係。気学的な距離の扱いはどこにも入っていない。

思想の断片は 1 か所だけある。`lib/areaContent.ts` の

```ts
/** 近すぎる相手は方位が定まらないので除く。同一市内の区など。 */
const MIN_KM = 5;
```

**決めるべきこと。**

1. 距離で作用の強弱を変えるのか、変えないのか（流派差がある）
2. 変えるなら、しきい値と重みをどこに置くか（`utils/` に 1 か所）
3. 「近すぎて方位が定まらない」帯を判定にも入れるか（今は表示から除くだけ）

**決まるまで実装しない。**しきい値は九星気学の判定そのものなので、
`CLAUDE.md` の「数値・しきい値・条件式に触らない」に当たる。

### F. 「引越し先を試算する」の入口を作る

使えていない、という指摘。原因は**最初に何を入れればいいか分からない**ことだと思われる。

## 3. 九星気学についての整理（実装ではなく前提の共有）

「東へ凶方位で移動 → 75 日 → 吉方位へ移動」で、最初の凶は相殺されるのか、という問い。

**流派で言うことが違う領域なので、サイトとして断定的に書かない。**
確実に言えるのは幾何のほうだけ。

### 第 2 移動が短いと、元の起点から見た方位は変わらない

京都を起点に計算した実測値。

```
東  30km → 南東  10km : 元の起点から E   ← まだ東の扇形の中
東  80km → 南東  30km : 元の起点から E   ← 同上
東 200km → 南東  80km : 元の起点から E   ← 同上
東  80km → 南東  80km : 元の起点から SE
東  10km → 南東  10km : 元の起点から SE
```

目安として、**第 2 移動が第 1 移動の 1.5 倍程度ないと扇形を出ない。**

75 日で基点が移る規則（実装済み）は「**次の移動をどこから測るか**」を決めるだけで、
「元の起点から見てどこにいるか」は別の話。ここを混同すると、
「吉方位へ動いたはずが、元の起点から見るとまだ凶方位の中」が起こる。

### 画面に出すとしたら

**提案：シミュレータで「元の起点から見た現在地の方位」を併記する。**
基点は移っても、元の起点からの方位は消えないという事実だけを示す。
相殺されるかどうかの解釈には踏み込まない。

これなら流派の判断をサイトが下さずに済み、利用者は自分の流派で解釈できる。
