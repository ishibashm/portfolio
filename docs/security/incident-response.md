# Leak and compromise response runbook

This is an owner-operated procedure. No keys, environment values, production records or remote settings were read or changed during this review.

1. **Declare and contain.** Assign an incident lead; record UTC times, affected deployment IDs and suspected scope. Use restricted incident storage. If active abuse is suspected, restrict affected routes at the edge or take the vulnerable feature offline. Preserve necessary evidence without copying payloads or secret values. Patch vulnerable dependencies before restoring traffic.
2. **Assess scope.** Determine whether the exposure was a browser bundle, public Git history, build artifact, server log, RSC source disclosure, DB policy, or executed server code. Treat code execution as possible access to every credential available to that process. Review provider audit logs, DB role activity, deployments and grant changes. A code review cannot establish whether production was exploited.
3. **Replace exposed credentials in their issuing systems.** Inventory credential *names* and consumers without recording values. Create replacements through provider dashboards/secret managers, update each authorized environment, validate consumers, then revoke old credentials promptly. With active misuse, revoke immediately and accept downtime. Do not put replacements in shell arguments, commits, tickets or chat.
4. **Supabase.** Identify whether the exposed item is a publishable/anon key, service-role/secret key, JWT signing material, or database password; they have different scopes. Follow current Supabase dashboard instructions for that project/key type. Revoke/rotate leaked privileged keys, update server-only consumers, review exposed schemas/storage/RPCs and RLS, and verify old credentials fail. Never move a privileged key into `NEXT_PUBLIC_*`. Signing-key changes may require session invalidation and a planned reauthentication window.
5. **Database and OAuth.** Rotate compromised DB-role passwords and invalidate affected pools. Revoke exposed Google/Gmail refresh tokens, OAuth clients/secrets, MCP grants and provider sessions as appropriate. Rotate leaked API-provider, cron/webhook, mail and deployment tokens; review billing and restrict scopes. Signing-key rotation alone does not necessarily revoke an already-issued provider token.
6. **Encryption keys need a migration plan.** Do not replace encryption/HMAC keys blindly: encrypted Gmail, personal memory, MCP state and saved user API keys may become unreadable. If confidentiality is lost, assume affected ciphertext can be decrypted. Where safe, use the existing versioned-key mechanism to read old data and re-encrypt with a new key; otherwise revoke/reconnect or delete state with owner approval. Retain old keys only for the bounded migration, then revoke. Backups need separate treatment.
7. **Eradicate and recover.** Redeploy a verified patched build under owner authorization, invalidate affected caches/artifacts, verify no secrets in browser assets, test unauthenticated/other-user denial and legitimate MCP/OAuth flows. Apply the reviewed RLS migration only after staging and backup checks. Restore traffic gradually and monitor errors, spending and denied requests.
8. **Communicate and learn.** Determine notification obligations with the appropriate privacy/legal owner based on actual data and jurisdictions; do not assume a universal deadline. Notify affected people through an approved channel with facts, impact and protective steps. Record root cause, timeline, access scope, revoked credential IDs (never values), validation and remaining actions. Review alerting and tests.

For a public Git leak, revoke first. Then coordinate history rewriting and removal of release/build artifacts with repository owners; a rewrite does not remove existing clones or caches. Historical personal information cannot be “rotated”; stop further distribution and assess notification and privacy remedies.

Recovery exit criteria: old credentials demonstrably rejected; patched dependencies verified; affected RLS/grants and owner checks tested; unauthorized access no longer succeeds; privacy-preserving monitoring active; owners assigned to outstanding actions. Keep the incident open if any required criterion remains unverified.
