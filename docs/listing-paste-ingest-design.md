# 賃貸候補の貼り付け取り込み・方位判定設計

設計日: 2026-09-21。対象: cloud-palette.com / ishibashm/portfolio。
状態: Phase 1 のローカル実装を追加（2026-09-21）。設計本文の方針を維持し、実装状況・未達事項は12節に記録。Phase 2 は未実装。

## 1. 結論と範囲

Phase 1 は **ユーザーが物件URLまたは住所を貼る → 所在地を確認する → 既存の方位・盤で判定する → 本人の候補履歴に保存する**。URLだけで所在地が分からない場合は住所入力または地図指定を求める。「URLを貼れば必ず物件の住所が自動取得できる」という仕様にはしない。

SUUMO / HOME'S / シャーメゾン / いい部屋ネットを含むポータルへのサーバー側スクレイピング・クロールは設計しない。個別URLであっても GET / HEAD、リダイレクト追跡、OGP、favicon、画像、JSON-LD、ブラウザ自動操作、外部抽出サービス経由の取得を行わない。クライアント側自動取得への置き換えも行わない。URLはユーザーの参照リンクであり、取得ジョブの指示ではない。

**Jev の有無で Phase 1 の基本設計は変わらない。方位角と盤の決定的計算には使わず、クリティカルパスから外す。** 導入するとしても任意の取り込み分類・優先度付けだけとし、Phase 2 のメール取り込みとともに別途評価する。

## 3. Phase 1 のユーザーフロー

1. `/relocation/arbitrage` の地点判定で「物件URL・住所」を1件貼り付ける。出発地、対象日、生年月日、盤設定は既存 `userSettings` の入力を使い、未設定なら入力を案内する。
2. 端末側でURL／住所／座標を分類・正規化する。URLの場合は参照リンクを保持し、読める地域情報があれば住所入力のヒントだけに使う。
3. 「このURLだけでは物件の住所を特定できません。掲載ページで確認した住所を入力するか、地図で場所を指定してください」と案内する。ページを開くのはユーザー自身の操作。住所は本人が入力し、タイトル・メモは任意。
4. 住所を既存ジオコード処理へ渡す。座標入力・地図クリックならジオコードを省略する。結果を地図上で本人が確認し、必要ならピンを直す。
5. 出発地から対象地点への真北基準の方位角・方位・距離と、選択日の盤の判定を表示する。候補への方位であり、部屋の窓・玄関の向きではない。
6. 「候補履歴に保存」で、ログイン済み本人の候補として保存する。匿名時は判定まで使えるが、新しい候補履歴のDB保存にはログインが必要。保存前の下書きはメモリのみとし、既存の地点保存とは区別する。ログイン遷移が必要なら入力が消える旨を示し、住所等を戻り先URLに載せない。
7. 個人候補一覧から参照リンクを開く、メモを編集する、削除する、現在の条件で再判定する。保存時の結果と現在の結果を区別する。

UI状態は `入力中 → 住所が必要 → 位置確認 → 判定可能 → 保存済み`。これは画面上の状態であり、全文や未完了下書きをDBへ逐次保存する仕様ではない。保存失敗時は入力を残し、成功するまで「保存済み」と表示しない。

### 精度・失敗時の扱い

- `source=municipality` は街の代表点。地図の初期位置には使えるが、物件所在地の確認を満たさない。住所またはピン指定が必要。
- `normalize` / `nominatim` 等の粗い点は既存の精度説明を表示する。町丁目までしか分からない場合は「概略位置」として本人が確認し、結果・履歴にもその制約を付ける。`gsi` も建物精度を保証するラベルにはせず地図確認する。
- 見つからない場合は住所修正・地図指定へ戻る。通信障害と該当なしは別表示。都道府県中心への無言のフォールバックはしない。
- 出発地と同一点は方位未定義として確定判定を保存しない。短距離・境界付近では位置を再確認する。短距離の注意は既存関数を使う。
- 生年月日や対象日等が不足したら方位のみ表示できるが、盤を「吉」と補完しない。Phase 1 の候補履歴保存は必要条件が揃ってから。URLだけの未処理候補保存は Phase 2 側の別検討。

## 4. 貼り付けから分かる情報と入力が必要な情報

| 入力                      | 通信なしで扱えるもの                                         | ユーザーに求めるもの                                            |
| ------------------------- | ------------------------------------------------------------ | --------------------------------------------------------------- |
| SUUMO等の詳細URL          | ホスト、パス、クエリ内の識別子。対応済みの構文なら地域ヒント | 原則として物件住所か座標・ピン。タイトル・メモは任意            |
| 一覧・検索URL             | 一覧らしい構文、対応済み地域コード                           | 対象の物件と所在地。検索条件を物件の属性として保存しない        |
| 短縮・追跡URL             | リンク文字列のみ                                             | 本人が開いてコピーした通常の詳細URL、または住所。自動展開しない |
| URL内の明示的な住所・座標 | 将来、既知構文に限り候補値を読む余地はある                   | 地図確認。Phase 1 では汎用クエリ推測をしない                    |
| 日本語住所                | 表記の正規化、住所検索への入力                               | 複数候補・概略位置の確認。番地を勝手に落とさない                |
| 緯度経度                  | 有限値・日本範囲の検証                                       | 地図確認                                                        |

HTMLを取得しないため、物件名・所在地・賃料・間取り・画像・募集状況はURLから分かったとみなさない。価格や募集終了の監視も行わない。タイトル・メモは利用者自身の短い覚え書きとし、ポータル本文のコピー欄にしない。

### 正規化

- URLは標準URLパーサーで解析し、保存は HTTPS のみ。認証情報入り、制御文字入り、localhost・プライベートIP等のローカル宛てを拒否する。既存 `normalizeSpotUrl` の規則を確認し共通化できる範囲を再利用する。
- スキーム・ホストの標準化、既知の追跡パラメーター（`utm_*` 等）の除去を行う。パスの大小文字や未知クエリを無条件に消さない。トークン・メールアドレス等の機微値が含まれるURLは通常URLへの貼り直しを求める。生URLの別保存はしない。
- フラグメントがルーティングに必要か不明なら、勝手に壊さず通常の詳細URLを求める。正規化後のリンクを保存前に表示する。
- URLの重複は本人の候補内だけで確認する。別サイトの同じ物件と推測して自動統合しない。住所のみの場合も座標だけで別部屋を統合しない。
- 住所は前後空白・数字表記等を既存の正規化へ渡す。部屋番号、氏名、電話番号は検索に不要であり送信対象から外す。住所本文は保存せず、確定した座標だけを候補に残す。

## 5. 方位・盤の再利用と保存結果

判定入力は `baseLat/baseLon`, `targetLat/targetLon`, `birthDate`, `targetDate`, `useClassical`, `directionFilterMode`, `tenchusatsuMode`, `involuntaryMove`。現在の arbitrage と同じ型・既定値・日付解釈を使う。候補用に `RelocationHistory` の別の計算経路をコピーしない。

方位は `bearingBetween` の値を丸める前に、`directionFromBearing(bearing, useClassical ? "traditional" : "physical")` で選ぶ。盤は `computeDayKigaku` の同じ方位セルから取得する。真北と磁北を混同せず、磁北の表示があっても判定本体には使わない。

保存APIも同じ純粋計算をサーバーで再実行し、クライアントから送られた tier や方位を信用しない。必要なら既存計算を環境非依存の共通モジュールへ整理するが、数式・既定値は変更しない。ブラウザの重い暦エンジンは既存同様に遅延読込とする。

保存する `judgment` は許可キーだけのバージョン付きスナップショットとする。

- `schemaVersion`, `engineVersion`, `evaluatedAt`。
- 入力条件の最小記録: 出発地座標、対象日、盤・フィルター等の設定。生年月日そのものは複製せず、必要なら計算に用いた本命星・空亡等の派生値のみ。これらも個人情報として扱う。
- 結果: 真北方位角、方位、tier、blocked、doyouSatsu、距離、位置の出典・概略フラグ・確認時刻。年/月/日層の内訳を足す場合も既存判定結果から取る。

出発地や日付が変われば過去の判定を現在の答えとして使わない。候補1件は「そのときの1回の検討記録」とし、座標・判定は保存後不変。再判定のプレビューは上書きせず、「新しい条件で履歴保存」なら新規レコードにする。タイトル・メモだけを編集可能とする。

## 6. データモデル案（Prisma 志向）

以下は設計時のモデル案。実装モデルには冪等性検証用の `requestDigest` と別テーブルの流量カウンターを追加した（12節）。

```prisma
model ListingCandidate {
  id          String   @id @default(uuid()) @db.Uuid
  userId      String   @db.Uuid
  url         String?  @db.VarChar(2048)
  title       String?  @db.VarChar(120)
  memo        String?  @db.VarChar(1000)
  lat         Float
  lon         Float
  bearingDeg  Float
  direction   String   @db.VarChar(2)
  judgment    Json
  requestKey  String   @db.Uuid
  createdAt   DateTime @default(now()) @db.Timestamptz(6)
  updatedAt   DateTime @updatedAt @db.Timestamptz(6)

  @@unique([userId, requestKey])
  @@index([userId, createdAt, id])
  @@map("listing_candidates")
}
```

`userId` は [getAuthUser / toUserId](../src/lib/userConfig.ts) が検証した Supabase の本人UUID。既存の NextAuth 系 `User` テーブルへの一致を仮定せず、既存地点保存と同様の所有者キーにする。退会時の本人レコード削除を削除フローに組み込む。`requestKey` は保存ボタンの通信再試行用で、同じキー・異なる内容は409、同じキー・同じ内容なら保存済みを返す。DBに所有者との複合一意制約を置く。

住所のみなら `url=null`。タイトル未指定なら一覧表示時に「候補 + 保存日」等を組み立てる。`direction` は8方位の列挙としてAPIで検証し、座標は有限値・日本範囲、方位角は `[0,360)` を検証する。`judgment` は任意JSONを受け入れず、サーバー生成の固定スキーマにする。

URL一意制約は設けない。同じURLでも異なる検討条件の履歴を保存できるため。保存前の重複案内と通信の冪等性は別に扱う。所有者・冪等性キー以外に、掲載情報・HTML・メール本文・画像・住所本文・埋め込みベクトルを持たない。

## 7. ページ／API案

入口は既存 `/relocation/arbitrage` の `SpotVerdict`。履歴一覧は兄弟ページ `/relocation/candidates` とする。地図クリックの `requestedPoint` と既存設定をそのまま使い、URLは別の参照欄へ収める。掲載一覧・全ユーザー横断の物件検索は復活させない。

新しい兄弟ページは本人ログイン用として設計し、既存 `NON_CORE_ROUTES` の管理者限定規則へ単純追加しない。APIで必ず本人を検証し、ページmiddlewareだけに保護を依存しない。

| メソッド・ルート（案）                               | 入出力・責務                                                                                                                                                                 |
| ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 端末内の貼り付け解析                                 | URL等の分類・正規化。汎用 `/fetch-url` API は作らない                                                                                                                        |
| `POST /api/relocation/candidates/geocode`            | `{address}` を受ける本人用の薄い入口。既存ジオコード処理を共有し、`{lat,lon,source}` を返す。URLは受け付けない                                                               |
| `POST /api/relocation/candidates`                    | `{requestKey,url?,title?,memo?,target:{lat,lon,source,approximate,confirmed},context:{...判定入力}}`。正規化・検証・再計算後に保存し201。生年月日・住所はログ/DBに複製しない |
| `GET /api/relocation/candidates?cursor=...&limit=20` | 本人の保存時スナップショットを新しい順に取得。最大50件・不透明cursor。毎回の自動再評価はしない                                                                               |
| `PATCH /api/relocation/candidates/:id`               | 本人の `title/memo` のみ更新。`updatedAt` による楽観ロック。所在地・参照URL修正は新候補として確認・保存                                                                      |
| `DELETE /api/relocation/candidates/:id`              | 本人の行を物理削除し204。他人の行と存在しない行は同じ404                                                                                                                     |

ジオコードのPOST入口は新しいプロバイダーを作るためではなく、住所をURL・アクセスログに残さず、認証・流量制御を置くためのもの。既存 `/api/geocode` の住所処理を共通化して利用する。現在の公開Nominatimフォールバックは新しい個人候補経路では無効とし、国土地理院等の利用条件に適合する既存処理だけを呼ぶ。不可なら手動ピン入力で続ける。匿名の既存地点判定の挙動変更はこの設計に含めない。

失敗は400（入力不正）、401（ログイン必要）、404（本人の候補なし）、409（条件不足・更新競合・冪等性キー衝突）、422（所在地未解決・同一点等）、429（上限、`Retry-After`）、503（外部検索障害）で区別。JSONの機械可読 `code` と日本語メッセージを返す。住所未解決と通信障害をともに「住所がない」と返さない。

## 8. Phase 2 のみ: 自分の通知メールからURLを取り込む

Phase 1 にはOAuth追加、Gmail API、メールジョブ、Jev接続を含めない。Phase 2 は以下の別機能として検討する。

1. ユーザー自身がGmailに送信元・件名等のフィルタを作り、物件通知専用ラベルを付ける。既存メールへの一括適用は既定で行わない。
2. 別途同意を得て読み取り専用で接続し、開始時点以後・指定ラベル・件数上限の範囲だけ読む。ラベルはアプリ側の取得範囲であり、OAuth権限そのものをラベルに限定する機構ではない。
3. MIMEを安全に解析し、テキストのURLまたはHTMLの `href` だけを抽出する。HTMLは描画せず、画像・添付・リンク先は取得しない。メール本文は処理メモリから破棄し、永続保存・ログ記録しない。
4. 決定的なホスト・構文ルールで重複や解除リンク等を除き、候補URLを本人に提示する。追跡URLは展開しない。読めないものは通常URLの手動貼り付けへ戻す。
5. 本人が選んだURLを Phase 1 の住所入力・位置確認へ渡す。メール由来だから住所が確定したとは扱わない。ジオコード・保存の自動一括実行はしない。

最初の版はプレビューを保存せず、確定した `ListingCandidate` だけを残す。後で自動定期取得を行う場合、接続情報・暗号化トークン・同期カーソル等は候補データと別管理し、メール本文の保管庫や共有物件DBを作らない。ユーザーが切断したらジョブ停止・トークン破棄を行い、候補の削除は本人が選べるようにする。

本文からURLを読むにはmetadataだけでは足りず、`gmail.readonly` はRestricted scopeに該当する。OAuth審査・必要なセキュリティ評価・データ利用条件は Phase 2 の公開前に確認する。既存のGoogleログインがメール閲覧の同意を含むと解釈しない。[Google公式: Gmail API scopes](https://developers.google.com/workspace/gmail/api/auth/scopes)

## 9. Jev の有無で設計は変わるか

**実質的には変わらない。推奨は Phase 1 を Jev なしで成立させ、後で効果が測れる場所だけ任意追加すること。** 住所不足はJevを入れても埋まらず、HTMLを取得してよい理由にもならない。方位角・盤・位置の実在確認・アクセス許可はコードと既存サービスで決める。

TypeSafe公式ではJevは状態と型付き質問を受け、Choice / Score等の構造化判定を返すモデルと説明されている。この性質から、以下の補助分類には使えると考える。ただし本サービスの日本語物件メールでの精度・速度は未検証。[公式概要](https://docs.typesafe.ai/introduction)、[API reference](https://docs.typesafe.ai/api)

| 任意の用途           | Jevの役割                                   | 最終確認                                            |
| -------------------- | ------------------------------------------- | --------------------------------------------------- |
| 物件メールか         | Choiceで物件通知／広告／その他／不明を提案  | ラベル・本人確認。分類失敗で削除しない              |
| 詳細URLらしいか      | 未知パス等の分類補助                        | URL検証と本人確認。取得許可や募集状況は判断できない |
| 住所として十分そうか | 入力補完の案内を選ぶ                        | 実際のジオコードと地図確認。座標を生成させない      |
| 優先度               | 本人が入力した条件・メモをScoreで並べ替える | 任意の表示順のみ。盤の吉凶スコアと混ぜない          |

薄い `IngestAdvisor` 境界を設け、出力を `classification / priority / confidence / reasonCode` 等の許可した型だけに変換する。これはアプリ内契約案でありJev APIの生スキーマではない。`LISTING_INGEST_JEV_ENABLED=false` を既定とし、本人の外部送信同意がなければ呼ばない。無効・鍵なし・タイムアウト・不正応答・低信頼時は `unknown` として通常入力に戻す。保存・判定は待たせず、Jev失敗で候補を捨てない。

外部へ送るのは必要最小限の匿名化した特徴や短い入力断片だけ。出発地座標、生年月日、メール全文、個人トークンを含むURLは送らない。伏せたため分類不能なら本人確認へ戻す。初期の提案タイムアウトは1秒、同期経路の自動再試行なし。導入判断は日本語データでの誤除外率、手修正率、p95遅延、費用、送信データの取り扱いを測ってから行う。

ユーザーが挙げた名称は同じ役割ではない。

- [typesafe-mcp](https://github.com/itsmostafa/typesafe-mcp) と [jev-mcp](https://github.com/jkudish/jev-mcp) はJev判定をMCPから呼ぶための別々の実装。開発時の試験には候補となるが、Next.jsの本番入力経路にMCPプロセスを必須追加する理由はない。採用時には対象リポジトリ・版・送信先を固定する。
- [jev-ultrafast](https://github.com/browser-use/jev-ultrafast) はJevが操作を選ぶブラウザエージェント。ポータル巡回・住所取得には採用しない。

この設計ではいずれもインストール・実行しない。Jevの価格・速度の数値保証や「型付き出力だから判定が正しい」という前提は置かない。

## 10. セキュリティ・プライバシー・利用条件

- **所有権:** 全CRUDでサーバー認証から所有者を決め、入力 `userId` は受け付けない。検索・更新・削除の条件に必ず本人UUIDを含める。Supabaseの直接公開アクセスは無効化し、必要な場合はRLSで本人に限定する。サービス権限のPrismaでも所有者条件は省略しない。
- **PII:** 出発地・候補座標、メモ、判定条件は個人情報。API応答は `no-store`、本文・URL・住所・座標・生年月日をログ、分析イベント、エラー収集、外部AIへ流さない。候補ページに公開共有、検索インデックス、サイトマップ掲載を設けない。
- **外部送信:** ジオコードには必要な住所だけを送る。氏名・部屋番号・出発地・プロフィールと結び付けて送らない。提供者の条件・保存可否・出典表記を実装時に確認する。既存コードにあること自体を利用許諾の根拠にしない。
- **Nominatim:** 公開サービスはPII送信を避ける規定があり、新しい候補経路では使わない。既存機能で使い続ける場合もアプリ全体1 req/s以下、識別可能なUA、出典表示、オートコンプリート禁止等を守る必要がある。[公式利用ポリシー](https://operations.osmfoundation.org/policies/nominatim/)
- **流量:** 初期案は保存・編集20回/分/人、ジオコード10回/分/人、読み取り60回/分/人、候補500件/人。プロバイダー上限がより厳しければそちらを優先。既存 `apiGuard` を参考に、複数インスタンス共通の制限とプロバイダー単位の総量制御を設ける。上限チェックと挿入は競合で越えないようトランザクション等で直列化する。
- **入力:** 1リクエスト1候補、JSON最大16KB、URL2048文字、タイトル120文字、メモ1000文字、住所検索入力256文字を初期上限とする。数値・列挙・日付を検証し、メモはプレーンテキストで描画する。HTML／Markdown埋め込みを許可しない。
- **CSRF / SSRF:** Cookie認証の変更操作に同一オリジン確認。URLはfetchもHEADもしないため任意URL取得の口を作らない。ブラウザ自動prefetchも無効。外部リンクは明示クリックのみ、`noopener noreferrer` と `no-referrer` を使う。
- **保存期間:** 候補は本人が削除・退会するまで保持。下書き・メール全文は保存しない。削除後のバックアップ残存期間は既存運用の実値を確認し、公開前に表示へ反映する。監査は処理種別・件数・成功/失敗コードに絞る。
- **規約境界:** ユーザー所有の候補記録は、ポータルの掲載情報を再利用する許可とは別。本文ダンプ、写真、説明文の再掲載、第三者公開、募集状況確認を実装しない。各社規約の全面的な適法性をこの設計だけで保証するものではなく、既存の停止方針を保ったまま、リンク表示等の該当条件を公開前に再確認する。確認できない追加機能は住所・地図の手入力で代替する。

## 11. 実装に進む場合の受け入れ条件

1. 4ポータルのURL、一覧URL、短縮URL、悪意あるURLを貼っても、ポータル・追跡先への通信が0件。URLがジオコーダーやJevへ無断転送されない。
2. 住所／ピンの同じ座標・日付・設定で、既存 `SpotVerdict`、プレビュー、保存APIの方位・tier・blocked・土用殺が一致する。既存 `geocodeUrlNotForwarded`、`userSpotUrlNeverFetched` 等の回帰観点を継承する。
3. 市区町村代表点だけでは物件位置確認が完了しない。概略位置・短距離・同一点・未設定条件・通信障害が区別される。
4. 他人のUUIDを指定しても読取・編集・削除できない。二重送信は1件となり、異なる判定条件の履歴は残せる。DB上限・レート制限を並行リクエストでも守る。
5. 住所・URL・メモ・座標がログや公開キャッシュに残らず、候補削除・退会が反映される。ポータル本文・画像・メール全文がDBに存在しない。
6. JevフラグOFF、鍵なし、障害時にも Phase 1 の全操作が成立する。メール接続なしでリリースできる。

Phase 1 の実装順は、入力分類と位置確認 → 既存判定の共有 → 本人限定保存 → 候補履歴。Phase 2 とJevの導入判断は独立して行う。

## 12. Phase 1 ローカル実装記録（2026-09-21）

### 実装した経路

- `/relocation/arbitrage` の `SpotVerdict` に貼り付け分類を接続。URLを保持し、所在地は座標入力・地図ピン・本人用POST住所検索から指定する。URLから市区町村代表点を物件所在地として自動確定しない。
- 候補ピンを地図に表示し、「地図の所在地を確認しました」の操作を保存条件にする。概略位置、同一点、条件不足、短距離・境界の注意を区別。タイトル・メモ・URL・候補下書きはメモリだけで保持し、既存UserSpotへの自動保存・移行はしない。
- `spotEvaluation.ts` は既存の方位・距離関数と盤のセル参照を共有するだけで、別の判定エンジンではない。保存APIは既存 `computeDayKigaku` を再実行する。ブラウザの暦エンジン遅延読み込みを維持。
- `ListingCandidate`、本人限定CRUD、本人のURL重複案内、一覧ページ、ページング、保存時の結果表示、現在条件での再判定を追加。再判定へのリンクに載るのは候補UUIDだけで、参照時にも所有者を検証する。
- 冪等性は所有者＋requestKeyのDB一意制約と入力ダイジェストで検査する。同じキー・同内容は保存済みを返し、異なる内容は409。タイトル・メモ編集はupdatedAtで競合を検出。座標・URL・保存時の判定は更新不可。
- PostgreSQLの本人単位advisory transaction lockで上限チェックと挿入を直列化。流量制限はプロセスメモリではなくDBの原子的な60秒カウンターで共有する。保存/編集/削除20回、読取60回、住所検索10回/人、候補500件。新しい候補経路のGSI総量は30回/分。
- JSON本文16KBをストリーム読込中に制限。個人APIはno-store、ログに本文や例外内容を出さない。履歴はnoindex・サイトマップ除外・robots除外。ポータルリンクは通常のa要素で、本人クリックのみ・no-referrer・noopener noreferrer。
- 「登録した内容を消す」に本人の候補履歴削除を追加。Supabase `auth.users` があるDBではmigrationが候補のON DELETE CASCADEと流量行削除トリガーを設定する。レガシーNextAuth Userへの外部キーは作らない。
- Jev・OAuth・メール処理は追加していない。Jev設定・鍵の有無によらず同じ処理経路になる。

### 導入手順と未確認事項

1. `prisma/migrations/20260921000000_listing_candidates/migration.sql` を対象DBで適用する。このリポジトリには従来Prisma migrations履歴がないため、既存DBへ最初から `migrate deploy` を流す前にbaselineを整理すること。従来のSQL運用で導入する場合は、このSQLを一度だけ実行する（BEGIN/COMMIT付き）。`db push` だけではRLS・権限剥奪・auth削除連動が導入されない。
2. `prisma generate` を実行してからアプリを起動する。今回Client生成とschema validateは実行済み。対象DBへのDDL実行・本番接続・push・PRは実施していない。
3. **住所検索は `LISTING_CANDIDATE_GSI_ENABLED=false` が既定。** 利用条件、個人住所の取扱い、結果の保存可否、既存経路も含めたプロバイダー全体の総量を運用者が確認してからtrueにする。今回はこの確認を完了していないため有効化していない。OFF時は503/GEOCODE_DISABLEDを表示し、地図ピン・座標で続けられる。公開Nominatimはこの経路から呼ばない。有効時は既存lookupGsiのみを使い、住所をアプリのGET URLには載せない。氏名・電話番号・建物名・部屋番号を除いた住所の入力を案内し、検知できる連絡先等は拒否する。任意の自由文からすべての氏名を識別する機能はない。
4. **未検証:** 実PostgreSQLでの同時実行、migrationの権限/RLS/退会連動、Supabase認証ユーザーによるブラウザでの一連動作。この環境には実行可能なローカルDB・認証設定がなく、APIテストはDBと認証をモックしている。これらの受け入れ確認はリリース前に必要。
5. **未確認:** バックアップの実保持期間と公開画面への反映、各ポータル参照リンクについての公開前の条件確認。住所・画像・掲載本文・メールを候補モデルへ格納する列は作っていないが、運用側アクセスログ/APMでリクエスト本文収集を無効にする設定も公開前に確認する。
