# AI接続管理画面の公開前確認

更新: 2026-10-15。対象は個人用MCPのDraft PR #1667。コードは実装済みだが既定では無効で、実DB・実ログイン・AIクライアントとの接続試験は未完了。公開済みと案内しない。

## 現在の配線

- `MCP_PERSONAL_ENABLED` が未設定または `false` の間、`/profile/connections`、`/api/mcp/connections`、個人用MCPとOAuth入口は404。公開 `/api/mcp` は別経路で継続する。
- 明示的に `true` とし、DB・鍵・静的OAuthクライアントなどの設定が揃った環境では、ページが `McpConnectionsPanel` を読み込み、Next Pages APIのNode入口が管理handlerを呼ぶ。`createMcpRuntime` が管理サービス・表示サービス・Node handlerを接続する。管理ページは動的表示でnoindex。実デプロイでキャッシュとサイトマップを再確認する。
- 管理APIは既存サイトのSupabaseログインをサーバーで検証し、正規Host/Originと管理用ヘッダーを要求する。同一originのCookie付き画面から、最大100件ずつ一覧、単一解除、すべて解除、選択範囲の縮小を行う。応答は `private, no-store`。AIのBearerトークンを管理操作の本人確認に使わない。
- 表示名は本人のクラウド保存 `presets` と静的登録済みクライアント名だけから引く。出生値・座標・トークンは管理画面へ渡さない。名前はテキストとして表示する。削除済みプロフィールもIDで識別して解除できる。
- 範囲縮小は1件以上を残す。すべてのチェックを外した場合は、確認後に既存の単一接続解除を呼ぶ。キャンセルは変更を送らない。APIとサービスも空配列を拒否し、DBの1〜100件制約と一致させる。解除ではアプリ側の許可を先に失効し、provider側の後処理が失敗しても再取得を拒否する。
- 操作後は先頭ページから再読込し、選択と確認状態を作り直す。失敗時は一覧を消し、操作が一部完了した可能性を示して手動再読込を促す。通常のサイトログアウトではMCP接続は解除されない。既にAIへ送った情報は回収できない。

## 公開前に必要な確認

1. Draftを最新 `master` と統合し、Node 22で全lint・型検査・build・テストを実行する。公開MCPに追加された `get_kanshi` を個人用の許可ツール、監査イベント、追加DDL、説明文にも一致させる。公開と個人用のツール一覧を実際のSDK経由で再確認する。
2. 実Postgresと検証用アカウントで、同時縮小・解除、別本人の分離、単一/全解除、期限切れ、部分障害、失効後の既存トークン拒否を確認する。既にMCP表がある場合、`CREATE TABLE IF NOT EXISTS` は監査イベント制約を更新しない。旧制約が確認できた場合だけ、オーナーがバックアップと短時間の排他ロックを確認して `prisma/sql/20261015_mcp_get_kanshi_audit_upgrade.sql` を別途検討する。未知の制約ならSQLは停止する。DDLとRLSの本番適用はオーナーの別作業であり、この文書だけでは実施しない。
3. 実SupabaseログインとChatGPT・Claude・Cursorで、接続→同意→プロフィール読取り→範囲縮小→解除→拒否→更新トークン失効を架空のプロフィールで確認する。各クライアントが静的OAuth登録を使えるかも確認する。
4. 実ブラウザーでTab/Space/Enter、確認後のフォーカス、狭い画面、スクリーンリーダー通知を確認する。現在のjsdomテストだけでアクセシビリティの実環境確認は完了しない。
5. 鍵管理、canonical Host/proxy、TLS、アクセスログ/APMの秘匿、no-store、サービスワーカー、期限掃除、切戻しをPRの配置手順どおり検証してからflagを有効にする。検証完了まで個人用を閉じたままにする。

個人用MCP全体の契約は `docs/mcp-personal.md`、オーナー実施の配置手順はPR #1667の本文を参照する。
